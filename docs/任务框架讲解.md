# 项目整体框架（验收讲解稿）

> 一句话总纲：**中断只搬运、队列做解耦、任务做业务、硬件做波形**——
> 一个「事件驱动 + 时间驱动」混合的 FreeRTOS 分层架构。

---

## 一、总体分层（自底向上）

```
┌─────────────────────────────────────────────────────────────┐
│ 应用层   4 个 FreeRTOS 任务（业务逻辑，可阻塞）                │
│          Task_CanRx / Task_Breath / Task_UartEcho / Task_Mpu │
├─────────────────────────────────────────────────────────────┤
│ 通信/解耦层  2 条队列 + 任务通知 + 协议解析 + JustFloat 组帧    │
├─────────────────────────────────────────────────────────────┤
│ 算法层   姿态解算（eMPL DMP / 互补滤波，宏开关热切换）          │
├─────────────────────────────────────────────────────────────┤
│ 板级驱动层  soft_i2c（DWT 时序） / mpu6050 / vofa_send        │
├─────────────────────────────────────────────────────────────┤
│ 硬件抽象层  HAL + 手写外设初始化（.ioc 仅作配置记录）           │
└─────────────────────────────────────────────────────────────┘
```

**分层原则**：依赖只准向下；上层不知道下层的引脚和寄存器，
下层不知道上层的业务——所以换收发器、换姿态算法、换传感器量程
都只动一层。

---

## 二、数据流全景图（讲解主线）

```
 【中断层：极短，只搬运，零业务】

  CAN 总线 ──CAN1_RX0_IRQHandler──帧──► xQueueSendFromISR ──┐
                                                            ▼
                                              ┌── 队列(6) ──┐
                                              └──────┬──────┘
                                                     ▼
  USB-TTL ──DMA循环接收──IDLE中断──行──► 队列(3) ─► Task_CanRx
                                            │       │ 帧头/帧尾/求和校验
                                            │       ▼
                                            │  xTaskNotify（置呼吸周期）
                                            │       │
                                            ▼       ▼
                                     Task_UartEcho  Task_Breath
                                     清洗后 DMA 回传     │ 改节拍参数
                                     "Receive Data：（%s）" ▼
                                              TIM7 1kHz ISR ──► TIM3 CCR
                                              （呼吸波形，纯硬件路径）

  MPU6050 ──软件IIC(PB0/PB1)──► Task_Mpu（vTaskDelayUntil 绝对 5ms）
                                   │ 原始六轴 → 姿态解算
                                   ▼
                              JustFloat 9ch 帧 ──DMA──► VOFA+
```

**讲解口诀**：数据永远是单向流——
`中断 → 队列 → 任务 → 外设`，没有反向轮询，没有全局变量竞态。

## 三、九个设计决策（每个都是加分点：问题 → 选择 → 代价）

### 1. 中断最小化：ISR 只做"搬运"
- **问题**：CAN 突发收帧时在中断里解析，会阻塞更低优先级中断、拉长最坏中断延迟。
- **选择**：ISR 只 `xQueueSendFromISR`（微秒级），解析搬进 `Task_CanRx`。
- **代价**：多一次上下文切换——用可预期的实时性换吞吐，值得。

### 2. 队列深度不是拍脑袋：按最坏情况算
- CAN 队列 **6**：一帧 8B @500kbps ≈ 160µs，6 帧 = 最坏 1ms 突发全缓冲，
  而 Task_CanRx 毫秒级就能消化 → 永不丢帧。
- 串口队列 **3**：任务书要求 3 行缓冲（按行回传）。

### 3. 任务通知 vs 信号量（考点）
一对一通信选 `xTaskNotify`：不用创建内核对象、省 RAM、比二值信号量
快约 45%，且天然带上"最新值"（呼吸周期），一对一时语义最清晰。

### 4. 双时钟域解耦（最核心的加分点）
- **业务时钟域**：FreeRTOS 调度（1ms tick）——管"什么时候该做什么事"。
- **波形时钟域**：TIM7 1kHz 硬件中断——管"呼吸灯每个台阶"。
- **效果**：即使 Task_Breath 永远不被调度（被高优先级任务饿死），
  呼吸灯照样平滑呼吸——任务书"任务二运行时呼吸灯照常"的关键保障。
- CAN 命令只改 TIM7 ISR 读的一个节拍参数，**改参数不改通路**。

### 5. vTaskDelayUntil 绝对周期（任务书核心考点）
- `vTaskDelay(5)` = 干完活再等 5ms，工作耗时会累积进周期 → 漂移；
- `vTaskDelayUntil(&lastWake, 5)` = 距上次唤醒点满 5ms，周期恒定；
- **证据链**：VOFA 时间戳相邻间隔恒定 5ms，一秒 200 个点，验收当场可验。

### 6. JustFloat 定长二进制帧：带宽账
- 9 通道 = 36B 数据 + 4B 帧尾 = 40B @115200 ≈ **3.5ms < 5ms 周期** ✓
- 文本打印一行就要 3~5ms 且长度不定，5ms 周期下必然积压丢帧。
- 结论：**协议选型由带宽预算倒推**，不是凭感觉。

### 7. 软件 IIC 而非硬件 I2C（任务书考点）
- 引脚任选（PB6~PB9 已被 CAN/串口占满）；
- 总线锁死可软件恢复（9 个时钟脉冲 + STOP，`SoftI2C_BusRecover`）；
- 时序完全可控（DWT 微秒延时，半位 2µs → 250kHz）；
- **代价**：5ms 周期里约 2ms CPU（14B 原始 + 34B FIFO）——可接受，
  且这正是"软件 IIC 的优势场景"而非劣势场景。

### 8. 防御式设计：两级看门狗 + 自愈
调试中真实踩到的两类硬件故障，全部变成自动化防护：
- **全零看门狗**：六轴物理上不可能同时全零（平放 z=+1g）→ 连续 40 帧
  全零 = SDA 被从机钳低（接触不良）→ 自动 9-clock 总线恢复 + 重初始化；
- **饱和看门狗**：多轴同时钉在满量程 = 数据通路锁死（本兼容芯片
  FIFO 溢出的真实行为）→ 200ms 确认后自动恢复；
- **初始化降级**：MPU 初始化失败只慢速重试，不拖垮其它三个任务——
  一个外设的故障被限制在自己的任务里。

### 9. 特性开关分层（工程素养）
姿态输出有两条链路：DMP（芯片内解算）和互补滤波（软件兜底），
用两级宏 `DMP_ENABLED` / `DMP_USE_OUTPUT` 控制——
换一颗真品 MPU6050，改一个宏重新编译即切回 DMP，业务代码零改动。
教训也写进了提交记录：**不用 DMP 输出就不进入 DMP 模式**
（FIFO 溢出会锁死兼容芯片的数据通路）。

## 四、任务一览表（讲解时配合板子演示）

| 任务 | 优先级 | 触发方式 | 周期/延迟 | 职责 |
|---|---|---|---|---|
| Task_CanRx | 高 | 队列阻塞 | 事件驱动 | CAN 帧校验解析 → 通知呼吸任务 |
| Task_Mpu | 高 | vTaskDelayUntil | **恒定 5ms** | 读六轴 → 姿态 → JustFloat |
| Task_Breath | 中 | 任务通知 | 事件驱动 | 改 TIM7 呼吸节拍 |
| Task_UartEcho | 中 | 队列阻塞 | 事件驱动 | 行清洗 + DMA 回传 |

优先级原则：**数据通路任务（怕丢数据）> 波形参数任务（改一下就行）**。

## 五、收尾话术（30 秒总结）

> 这个框架的本质是把"实时系统的三种时间尺度"分给三种机制：
> **微秒级的确定性给硬件**（TIM7 驱动 PWM、DMA 搬数据），
> **毫秒级的调度给 RTOS**（vTaskDelayUntil 绝对周期、按优先级抢占），
> **事件级的响应给中断+队列**（ISR 只投递，业务在任务里慢慢做）。
> 每一层只依赖下一层，每个决策都有量化的依据——
> 带宽预算决定协议、最坏延迟决定队列深度、故障模式决定看门狗。
